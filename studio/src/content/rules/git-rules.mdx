# Git 工作流规范

## 分支策略

- `main`：始终可部署——禁止直接推送
- `feat/描述`：新功能
- `fix/描述`：Bug 修复
- `docs/描述`：仅文档变更
- `refactor/描述`：代码重构
- 分支名：小写、连字符分隔、不超过 50 个字符

## 提交规范（Conventional Commits）

```
<类型>(<范围>): <简短描述>
```

- `feat`：新功能
- `fix`：Bug 修复
- `docs`：文档更新
- `style`：格式调整（不涉及逻辑）
- `refactor`：重构
- `test`：测试相关
- `chore`：其他维护

规范要求：
- 每次提交只包含一个逻辑变更
- 使用祈使语态，小写，不加句号：「添加功能」而非「添加了功能」
- 引用 Issue：`Closes #123`

## Pull Request 规范

- PR 标题遵循 Conventional Commits 格式
- 描述包含：改了什么、为什么改、如何测试
- 关联相关 Issue
- 提交 Review 前先自我审查
- PR 变更行数不超过 400 行——更大的改动要拆分

## 代码 Review

- Review 代码的正确性，不要 Review 风格（风格交给 Linter）
- Approve 意味着：我读过这段代码，它是正确的，我愿意维护它
- Request Changes 针对正确性问题
- 非阻塞的改进建议用 Suggestion 标注

## 合并规范

- Feature 分支使用 Squash Merge（保持历史干净）
- 长期维护分支使用 Merge Commit
- Feature 分支同步 main 时使用 Rebase
- 合并后删除分支
